# Agent Note: SDK cohort 0.2.1-alpha.5

Status: implemented

## Problem

The repository declared the `0.1.7-rc.1` cohort while the family's approved
target is `0.2.1-alpha.5` (npm `next`; the later `0.2.1-rc.1` is explicitly
not the target). The declared floor, the `@deepseek-ai/dsh` host peer, the
consumed SDK devDependencies, the README badges and the release-age ledger
all named the old cohort, and a lockfile regeneration was required to know
which packages the new cohort actually resolves here — the 0.1.7 graph and
the 0.2.1 graph differ by more than a version literal.

## Decision

The whole cohort moves to `0.2.1-alpha.5` in one change, on the local branch
`feat/dsh-0.2.1-alpha.5` of the isolated worktree. No version bump, no
publish, no push.

**One cohort, one literal.** `dsh.engines.dsh` (`>=0.2.1-alpha.5`), the
`@deepseek-ai/dsh` host peer, and the eleven consumed SDK devDependencies
(`dsh-api-remotes`, `dsh-api-session-controller`, `dsh-api-workspace-controller`,
`dsh-client-connection`, `dsh-client-locale`, `dsh-client-store`,
`dsh-client-ui-primitives`, `dsh-client-ui-renderer`, `dsh-client-ui-settings`,
`dsh-client-ui-slots`, `dsh-settings`) move together; the README badge in both
languages moves to the shields form `0.2.1--alpha.5` with `README.i18n.yaml`
re-recorded. `@deepseek-ai/cordis` (`^4.0.4`) does not move: it is not part of
the cohort literal, and both 4.0.4 and the cohort's transitive 4.0.5-alpha.2
resolve.

**No SDK source surface to repair.** This repository is an index data
source: `src/index.ts` imports only the `cordis` type and the generated
`mount-once` copy, and the package ships no client bundle. There is no
registry API, no UI surface and no wire format that consumes the SDK beyond
the inert cordis row, so the cohort move touches manifests, badges, the
ledger and the lockfile — no source file.

**The release-age ledger is reconciled against the regenerated lockfile, not
just re-versioned.** All `@deepseek-ai/dsh-*` rows moved to
`@0.2.1-alpha.5`; the install appended the rows for packages new in this
repository's 0.2.1 graph (for example `dsh-api-remote-access`,
`dsh-client-product-analytics`, `dsh-plugin-market*`, `dsh-util-code-language`,
`dsh-working-directory`). Manual alignment followed the resolved set:
`cordis` and `cosmokit` became unions (`4.0.4 || 4.0.5-alpha.2`,
`1.8.5 || 1.8.6-alpha.2`) because both versions resolve at once;
`cordis-plugin-include` (1.0.10-alpha.2), `cordis-plugin-loader`
(1.0.6-alpha.2), `cordis-plugin-group` (1.0.5-alpha.2), `cordis-plugin-timer`
(1.1.7-alpha.2), `schemastery` (3.18.5-alpha.2) and the six `libreoffice-kit`
rows (0.1.5) replaced versions the new graph no longer resolves; the five
`node-addon-system@0.1.2` platform rows were appended. Seven rows were
removed because upstream dropped those packages from the consumed subgraph
and the regenerated lockfile confirms none of them resolve here any more:
`dsh-hook-protocol`, `dsh-hooks-claude-code`, `dsh-hooks-codex`,
`dsh-invariants`, `dsh-subagent-in-process-driver`, `dsh-webhook`,
`dsh-webhook-github`. Unlike the dsh-presets repository, the
`dsh-client-store` row stays: this repository consumes that package directly
and it still resolves. A reconciliation script then proved the ledger covers
exactly the resolved `@deepseek-ai/*` set: no missing exclusions, no stale
rows.

**The shell's frozen module table grew, and the mirror moved with it.**
The published `dsh-web-frontend@0.2.1-alpha.5` dist bundle was inspected the
same way the comment describes: its `staticModules` table has two rows the
0.1.7-rc.1 and 0.2.0-rc.2 tables lack — `zod` and `@tanstack/react-virtual`.
`shared/web-platform.ts` therefore extends `PLATFORM_MODULES` to the full
11-row table and re-anchors its provenance comment to the 0.2.1-alpha.5
bundle. This package builds no client bundle and imports neither specifier,
so the rebuilt `lib/index.js` is byte-identical to the committed artifact;
the extension is forward drift prevention.

## Alternatives considered

**Keep `PLATFORM_MODULES` at nine rows and only reword the comment.**
Rejected: the list exists so module identities cannot drift from the shell's
frozen table, and a mirror asserting equivalence while omitting seeded rows
would be a false claim the next import would trip over.

**Leave the stale ledger rows in place.** Rejected: an exclusion for a
package the lockfile no longer contains is dead weight that obscures review,
and the ledger's contract is that it mirrors this repository's install graph.

**Carry the new transitive pins as unions with the old versions.** Rejected
where the old version no longer resolves (cordis-plugin-*, schemastery,
libreoffice-kit): the union form is for packages whose graph legitimately
resolves several versions at once, like cordis and cosmokit here.

**Move to `0.2.1-rc.1`.** Rejected by the task brief: 0.2.1-alpha.5 is the
approved cohort, rc.1 is not pursued.

## Consequences

- `pnpm install --prefer-offline` regenerated the lockfile at the new cohort;
  `pnpm typecheck`, `pnpm build`, `pnpm test` (2 tests), `pnpm community:check`
  (140 entries), the index contract suite (`node --test
  scripts/community-index.test.mjs`, 9 tests) and the CI supply-chain form
  (`pnpm install --frozen-lockfile --ignore-scripts`) all pass on the
  committed tree. The rebuilt `lib/` is byte-identical, so the committed
  artifact stays valid.
- Historical narratives that name the old cohort (docs/release-notes, earlier
  notes) are not rewritten.
- Cross-repository: the dsh-web family's own `shared/web-platform.ts` and the
  `TARGET_SHELL_STATIC_MODULES` list in `shared/tests/web-platform.spec.ts`
  need the same two rows when the main repository adapts to 0.2.1-alpha.5 —
  the recorded 0.2.0-rc.2 note states the table was unchanged between those
  cohorts, which stops being true at 0.2.1-alpha.5. The two satellite copies
  updated here lead that change; keeping the family copy convergent is main
  repository work.
- Nothing was published and no `@linxin666/*` version changed; integrating
  this branch is a maintainer decision, as is moving the dsh-web submodule
  pin afterwards.
